# 特徵集合是開放的，框架核心不認得任何具體特徵

新增一種特徵不應該改到框架。框架核心只處理「相依關係、執行順序、過時傳播」，完全不知道 Hole、Fillet、AAG 是什麼；每個 Recognizer 向框架註冊自己、宣告它依賴誰。

## Considered Options

- **開放的註冊機制**（採用）— 每個 Recognizer 註冊時宣告名稱與相依，框架配發 `FeatureId`，核心只以 id 運作。
- **封閉的 `enum FeatureType` + Visitor** — 特徵種類寫死在核心，用 Visitor 對各型別分派處理。

## 為什麼

封閉 enum 讓加一種特徵要同時改好幾個地方，而且全部在核心層：enum 本身、字串轉換、Visitor 的每個 `visit()`、建立演算法的 factory switch、以及手寫的相依關係。

其中 **Visitor 模式是關鍵阻礙**：它的前提就是型別集合封閉——每加一種特徵，所有 visitor 都得跟著改。這與「可擴充的辨識框架」這個目標直接衝突。因此改由每個結果自己負責描述自己（`describe()`）。

相依關係也不寫在核心，而是由各個 Recognizer 宣告，核心只在註冊時驗證整張圖無環。

## Consequences

- 框架失去編譯期的特徵型別檢查：核心以註冊時取得的識別子操作特徵，打錯名字要到執行期才會發現。具體型別的知識集中在呼叫端與 Recognizer 內部。
- 驗收條件因此很明確：**新增一種特徵時，改動集中在「新增一個 Recognizer 檔案」加上「在組裝點註冊一行」**；相依圖、執行排序、過時傳播這些核心邏輯不需要跟著改。目標是改動集中，不是追求零改動。
